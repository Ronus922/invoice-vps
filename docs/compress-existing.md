# דחיסה רטרואקטיבית של קבצים שמורים

כלי חד-פעמי (`scripts/compress-existing.ts`) שמקטין קבצים שכבר נמצאים ב-bucket `invoice-files`: תמונות JPG עד כ-300KB, ו-PDF סרוק עד 150dpi. **החלפה במקום**: אותו נתיב, אותו `file_name`, אותו Content-Type, בלי שום כתיבה ל-DB.

סטטוס: שלב 0 וה-dry-run בוצעו (2026-11-09). **`--apply` מומש ונבדק רק מול אחסון מדומה; הוא לא הופעל מעולם על Storage אמיתי.** הפעלתו דורשת אישור מפורש של רונן, קודם `--limit 20` ורק אחר כך מלא.

## החלטות סגורות (רונן, 2026-11-09)
- כל הקבצים, כולל PDF טקסטואליים: בלי רסטור, שכבת הטקסט נשמרת.
- החלפה במקום (אותו נתיב).
- תמונות עד 300KB; PDF סרוק 150dpi.
- מחליפים רק אם החיסכון **גדול מ-15%** (בדיוק 15% = דילוג).
- גיבוי tar.gz זמני שנמחק אוטומטית אחרי בדיקת שלמות.
- סדר: dry-run ← `--limit 20` ← מלא.

## הרצה
```bash
# dry-run (ברירת מחדל): קורא מהמסד (session לקריאה בלבד) ומ-Storage, לא כותב כלום
pnpm exec tsx scripts/compress-existing.ts --env-file /var/www/invoice/.env.local --report /tmp/dry
pnpm exec tsx scripts/compress-existing.ts --limit 20 ...        # מדגם של 20 קבצים, מכל הסוגים

# החלפה (רק באישור): דורש --limit N או --all, ולעולם לא ברירת מחדל
pnpm exec tsx scripts/compress-existing.ts --apply --limit 20 --keep-backup ...
pnpm exec tsx scripts/compress-existing.ts --apply --all ...
```
דגלים: `--dry-run` · `--apply` · `--limit N` · `--all` (רק עם `--apply`) · `--keep-backup` (רק עם `--apply`) · `--concurrency N` (4) · `--text-image-dpi N` (כבוי) · `--report FILE` (כותב `.json` ו-`.tsv`) · `--env-file FILE` · `--backup-dir DIR` (`/var/backups/invoice-precompress`). שילובים סותרים, דגל לא מוכר וערך חסר נדחים, ו-`--apply` בלי `--limit`/`--all` נדחה.

**לפני `--apply` ראשון:** `/var/backups` שייך ל-root, ולכן צריך ליצור את תיקיית הגיבוי פעם אחת (`sudo install -d -o ubuntu -m 700 /var/backups/invoice-precompress`) או לתת `--backup-dir` אחר. הסקריפט בודק זאת, ובודק מקום פנוי, **לפני שנוגע בקובץ אחד**. בשלב `--limit 20` מומלץ `--keep-backup`: הגיבוי מאומת ונשאר, כדי שאפשר יהיה לעיין בתוצאות לפני שמוחקים אותו.

הסקריפט לוקח מקובץ ה-env רק שלושה מפתחות (`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DIRECT_URL`) ולא מדפיס אותם. הוא דורש את כלי poppler (`pdftotext`, `pdfinfo`, `pdftoppm`) ומסרב לרוץ בלעדיהם: בדיקת השלמות לא מדולגת בשקט.

## מה dry-run מבטיח, ובאיזה מנגנון
- ה-DB: `psql` עם `default_transaction_read_only=on` ו-SELECT יחיד. הכתיבה נחסמת בשרת, גם אם הייתה טעות בשאילתה.
- Storage: ה-dry-run מקבל אובייקט `ReadStore` בלבד (`list`, `download`). אובייקט הכתיבה (`WriteStore`) נבנה רק עם `--apply`, כך ש"לא כותב" הוא תכונה של המבנה ולא הבטחה. אף אחד משני האדפטרים לא קורא ל-`remove`.
- הכלי לא מוחק ולא נוגע בשום אובייקט שאין לו שורה בטבלה.

## כללי ההחלטה (`src/lib/compress/decision.ts`)
לכל קובץ: `id`, סוג, גודל לפני, גודל אחרי, % חיסכון, החלטה. הסדר קובע, וכלל איסור גובר על כל חישוב גודל:

| דילוג | משמעות |
|---|---|
| `source-scan` | שורת `source='scan'`: כבר נדחסה בצינור הסריקה (JPEG ≤300KB, בלי metadata) |
| `signed-pdf` | **PDF חתום דיגיטלית**: כתיבה מחדש שוברת את החתימה, ולכן לא נוגעים. רק נמדד מה היה נחסך |
| `encrypted-pdf` | מוצפן |
| `pdfa-1` | PDF/A-1 אוסר object streams, וכתיבה מחדש הייתה מפסיקה אותו להיות מה שהוא טוען (9 קבצים בדלי) |
| `size-mismatch` | הקובץ שירד שונה בגודל ממה שה-bucket מדווח: לא האובייקט שחשבנו, לא מעבדים |
| `apply-failed` | רק ב-`--apply`: ההחלפה שוחזרה, או שההרצה נעצרה לפניה |
| `unsupported-type` | PNG / HEIC / WEBP / GIF / לא מזוהה: אין מנוע (ואין שורות כאלה היום) |
| `within-target` | JPG שכבר עד 300KB: לא מקודדים מחדש (אין סיבה לאבד איכות) |
| `engine-failed` / `integrity-failed` | המנוע נכשל, או שהתוצר נכשל בבדיקת השלמות |
| `not-smaller` / `below-threshold` | התוצר לא קטן יותר / חיסכון של 15% או פחות |

סוג הקובץ נקבע לפי magic bytes, לא לפי סיומת או Content-Type (ל-12 PDF-ים יש `application/octet-stream`).

## המנועים
- **קריאה מ-Storage** מנסה שוב עד 3 פעמים (קריאות הן idempotent); העלאה לא.
- **JPG** (`jpeg.ts`, sharp): אותם קבועים כמו צינור הסריקה (איכות 82 ← 76 ← 70 ← 64; גדלים 1600 ← 1280), אבל: בלי `normalise()` (המסמך נשאר נראה כמו שהיה); השלב הראשון שומר על הרזולוציה של התמונה (עד 2048px, כמו `upload.ts`), כך שאיכות נבחנת לפני ויתור על פיקסלים; EXIF מיושם ומוסר; progressive mozjpeg. הרצפה (1280px, איכות 64) מתקבלת גם אם היא כבדה מ-300KB.
- **PDF** (`pdf.ts`, pdf-lib + sharp): נוגע רק ב-(1) מבנה הקובץ, שנשמר מחדש עם object streams דחוסים; (2) ב-image XObjects של PDF סרוק. תוכן עמוד, פונטים ושכבת הטקסט לא נקראים ולא נכתבים. הרזולוציה נחסמת לפי **גודל העמוד** (תמונה לא יכולה לעבור "כל העמוד ב-150dpi"), בלי לפרסר את זרמי התוכן. זה שמרני: תמונה שמוצגת קטנה מהעמוד לא מוקטנת.
  - נטען במצב קפדני (`throwOnInvalidObject: true`): אובייקט שלא ניתן לפרסר נכשל במקום להידלג בשקט. מגבלות משאבים: פענוח Flate נעצר בגודל שתמונה תקינה יכולה להיות (פצצת deflate במייל לא תאכל זיכרון), ותמונה מעל 150M דגימות נשארת כמו שהיא.
  - אין נגיעה ב: תמונה עם `/Matte` או עם מסכת רכות שיש לה `/Matte`; JPEG עם `/DecodeParms` (למשל `/ColorTransform`).
  - רשימה לבנה בלבד: DCT (גווני אפור / RGB / ICC עם N=1,3) ו-Flate גולמי 8bpc (Gray / RGB / CMYK / ICC / Cal). `Indexed`, `ImageMask`, `/Mask`, CCITT, JBIG2, LZW, `DCT+Flate` ו-CMYK-JPEG נשארים כמו שהם.
  - Flate: הדגימות מפוענחות, מוקטנות בממוצע שטח (ליניארי, ולכן לא משנה את משמעות `/Decode`), ונארזות מחדש עם predictor 15. DCT: sharp, בסיסי (לא progressive, לתאימות עם כל הצופים).
- **למה לא ghostscript / qpdf / mupdf**: הראשונים לא מותקנים בשרת (התקנת חבילה = החלטה של רונן), ו-ghostscript כותב מחדש כל פונט וכל זרם תוכן, בדיוק ההפך מ-"שכבת הטקסט נשמרת". mupdf.js הוא AGPL, כ-14MB WASM, בלי API של הקטנת תמונות.

## בדיקת שלמות (לכל קובץ, לפני כל החלפה)
- **תמונה** (`verifyJpeg`): התוצר מפוענח עד הסוף, הוא JPEG, יחס הגובה-רוחב נשמר (עד 1.5%), וגם תמונות ממוזערות 64×64 באפור קרובות (סטייה ממוצעת ≤14 מתוך 255).
- **PDF** (`pdf-verify.ts`, poppler: קורא עצמאי, לא הספרייה שכתבה את הקובץ): נפתח; אותו מספר עמודים; **שכבת הטקסט זהה** (`pdftotext` לפני = אחרי); אותם פונטים (`pdffonts`), אותם קבצים מוטמעים (`pdfdetach`) ואותו מספר מיקומי תמונה (`pdfimages`); וכל העמודים (עד 30; הארוך בדלי הוא 8) מרונדרים ב-60dpi ומושווים פיקסל-פיקסל.
  - **שתי שאלות נפרדות.** (1) האם הכתיבה מחדש של pdf-lib שינתה משהו? הקובץ נשמר גם **בלי לגעת באף תמונה**, והרינדור שלו חייב להיות **זהה** לקובץ המקורי (סטייה ≤0.02) בכל מקרה, גם כשאחר כך תמונה מוקטנת; כך קו או חותמת שנשמטו לא מסתתרים מאחורי הסבילות שהקטנת תמונה דורשת. (2) האם התמונה המוקטנת עדיין אותו עמוד? מושווה לגרסה המבנית, בסבילות 10.
  - **תמונה:** `verifyJpeg` בודק גם את חלק הפיקסלים הכהים (דיו) — סטייה ממוצעת על דף שרובו נייר לבן לא תופסת פלט ריק. סף: סטייה ממוצעת ≤6, הפרש דיו ≤0.8% (ב-92 התמונות האמיתיות הגרוע ביותר הוא 1.4 ו-0.28%).
- למה זה לא מיותר: pdf-lib מדלג בשקט על אובייקט שהוא לא מצליח לפרסר. שלושה תלושי שכר של Gnostice איבדו כמחצית מהטקסט אחרי שמירה מחדש, ונתפסו רק בגלל בדיקת הטקסט.

## `--apply` (ממומש, לא הופעל)
לכל קובץ שהוחלט להחליף, לפי הסדר: (1) המקור נכתב לדיסק ל-`<backup-dir>/<timestamp>/files/…` עם hash ב-`manifest.jsonl`. אם זה נכשל, האובייקט לא נוגע וההרצה נעצרת; (2) העלאה עם `upsert` לאותו נתיב, **עם ה-Content-Type וה-cacheControl הקיימים** (הכלי לא "מתקן" את `octet-stream` מאחורי הגב); (3) הורדה חוזרת והשוואת SHA-256 לתוצר; (4) אי-התאמה ← המקור מועלה בחזרה ומאומת, ואם גם זה נכשל, הכתיבה נעצרת לגמרי.

בסוף: המקורות נארזים ל-`originals.tar.gz`, הארכיון נפרס לתיקיית ביניים ונבדק hash-hash מול ה-manifest, ה-bucket נקרא שוב ובודקים שגודל כל אובייקט שהוחלף הוא מה שנכתב. **רק אם הכול עבר, הגיבוי נמחק אוטומטית** (אלא אם ניתן `--keep-backup`). כל כשל משאיר אותו במקומו ומדפיס את הנתיב (קוד יציאה 1). הדו"ח (`--report`) נכתב **לפני** שהגיבוי נשפט, ואם ההרצה קרסה באמצע, הודעת השגיאה מציינת איפה הגיבוי. כל קובץ מקור נכתב ל-disk עם fsync לפני שהאובייקט שלו נוגע.

## מה משתנה ומה לא, לשאר חלקי המערכת
| צרכן | מה קורה אחרי החלפה במקום |
|---|---|
| תצוגה / הורדה (`/api/file`) | מקבל את הקובץ החדש. אין שינוי בנתיב |
| ZIP (`ExportToolbar`) | שם הערך = `file_name` (לא משתנה), התוכן הוא החדש |
| מייל לרו"ח (`accountant-send`) | שם הקובץ = `file_name`; ה-MIME = ה-Content-Type של האובייקט (נשמר). מיילים שכבר נשלחו לא משתנים |
| גיבוי Drive (`backup-to-drive`) | **לא מתעדכן** לשורות שכבר גובו (`drive_file_id` קיים ← דילוג, "Layer 1"). עותקי Drive הישנים נשארים בגודל המקורי; שורות שטרם גובו יעלו את הקובץ החדש |
| בדיקת כפילות (`UploadZone`, `check:dupes`) | לפי `file_name` וחתימת שדות, לא לפי hash: ללא שינוי |
| `extract-invoice` / סקריפטי re-extract | קוראים את הקובץ הדחוס. JPG עד 2048px ו-PDF סרוק ב-150dpi הם בטווח OCR רגיל |

**המרת PNG/HEIC ל-JPG: לא מומלצת, וגם אין בה צורך.** בטבלה אין אף שורה כזו (כל 140 התמונות הן `.jpg`; העלאה מהדפדפן ממירה ל-JPG, והסריקה שומרת JPEG). המרה הייתה מחייבת שינוי נתיב וסיומת ← כתיבה ל-DB, `file_name` שונה ← שם ב-ZIP/מייל/Drive שונה, Layer 2 ב-Drive לא מזהה עוד "אותו קובץ" ← כפילויות, ובדיקת הכפילות ב-UploadZone לפי שם מפסיקה להתאים. ה-13 PNG בדלי הם יתומים (בלי שורה).
